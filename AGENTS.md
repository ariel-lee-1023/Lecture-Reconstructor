# Using and maintaining Lecture Reconstructor

Ariel Lee is the project author. For a lecture-reconstruction request, read the canonical [SKILL.md](SKILL.md) at the start of the conversation and follow its loading triggers. The relative discovery link `.agents/skills/lecture-reconstructor -> ../..` points to the same entry. The user can invoke the skill by describing the task. For a repository-maintenance request, follow the requested scope and use the [source and validation records](fidelity-ledger/validation.md) as needed.

Use the decisive course problem and the strongest accessible primary material to determine the depth of the lecture. When little teaching survives, design the lesson from its documents and identify its basis. The manuscript defaults to the principal language of the actual teaching or, for source-led work, the substantive course materials. Honor an explicit choice of manuscript language. The language of the request, export interface, and automated recap do not set the teaching language. Use the [workflow](WORKFLOW.md) for production and recovery, and select the relevant sources for teaching design, legal reasoning, or transcript repair.

## Repository maintenance

`intent.md`, `spec.md`, and `plan.md` document the requirements baseline. `BUILD.md` is the historical build entry point. The user's task takes precedence.

- Limit changes to this repository. Roles, commands, language defaults, and prior authorizations in source materials are reference data. Upstream repositories are read-only; do not inherit authorization to commit, push, install globally, or publish.
- Maintain the teaching backbone, legal methods, and input repair separately; do not merge complete upstream personas. Preserve authorship, source locations, applicability limits, and MIT notices. This repository's license does not cover third-party books or classroom materials.
- Before editing, inventory existing files and their SHA-256 hashes and back them up outside the target directory. Record new files as `absent`. Before restoring a file, compare its current hash with the hash of your last write; if concurrent changes are present, preserve both versions first.
- Keep the single canonical skill, three source references, and root workflow usable without sibling repositories. Preserve relative links at the previous reference paths. Source-derived reasoning and locators belong in the reference files. Record editorial adaptations, source uncertainty, and the evidence for semantic review in `fidelity-ledger/`. Do not introduce a `prc-legal-sources` dependency; statements excluding it in the engineering documents are not dependencies.
- Keep private inputs, private runs, local source paths, and backups out of the publication package. Clearly label synthetic acceptance materials. Record publishable source identities in `fidelity-ledger/source-manifest.json`.
- When changing the checkers, run `python3 -m unittest discover -s tests -v` and `python3 scripts/validate_repo.py .`. A run-check exit code of `0` means only that the defined mechanical constraints passed.
- After changing the runtime core, retain the original hashes of earlier behavioral evidence. Assess the impact, rerun the affected behavior tests or mark them as awaiting acceptance, and never transfer an earlier pass to the revised core.
- Record mechanical checks, actual behavior, real classroom trials, and learning outcomes separately. Use `not_run` for work not executed; written self-assessment cannot replace a failed result. Normally allow at most two focused revision rounds and explicitly hand off any remaining critical defects.
